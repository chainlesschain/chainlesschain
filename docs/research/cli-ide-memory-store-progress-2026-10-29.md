## 实现

磁盘 authority 使用既有的 `withFileLockAsync`，锁覆盖异步回调直到结束。查询约每 8ms 在分片间让出事件循环，Stop 可以打断索引遍历、快照捕获、分片解码及锁等待。捕获完成前持续持锁；捕获后仅解码当前查询拥有的字节，避免并发 GC 或更新混入其他 generation。取消返回错误，不能将部分结果或迟到成功当成完成。

取消信号作为 `recallMemory(request, { signal })` 的第二个宿主参数，经 CLI 服务、provider context 和 Memory port 传递；不会加入严格校验的序列化 `MemoryRecallRequest`。provider context 在各异步阶段完成后再次检查取消，防止 Stop 后返回模型上下文计划。本地 CLI 验证使用工作区子包源码，与根工作区安装的解析方式一致；已发布的 `0.1.10` 不因此自动具备新参数的行为。

Windows 目录校验继续对每级祖先执行 `lstat`，并对完整目标目录执行一次 native realpath。完整路径解析仍经过所有祖先，避免每个分片反复解析相同的每级前缀。保留目录身份、链接、文件摘要与 generation 校验；补充真实 junction 位于已有深层目录祖先、且适配器将其误报为普通目录的回归。

这仍是分片间协作式取消：单个同步文件系统调用、单分片 JSON 校验、旧格式迁移及 kernel 排名没有变成可抢占计算。当前测量不能证明这些最坏情况符合硬性取消期限。

回归覆盖预先取消、两种缓存策略、活 owner 的锁等待取消、解码中取消不返回部分结果、同进程 writer 在 reader 让出时保持快照、provider recall 的取消参数传递，以及原有损坏索引 / 分片、CAS、权限过滤、图片上下文和杀进程后删除恢复。新增 Windows 深层 junction 用例通过；跳过的是不适用于 Windows 的目录 fsync 故障用例。验证清单与实现摘要见[验证回执](./cli/evidence/memory-store-2026-10-29/verification.json)，补充原始回归见 [CLI Node TAP](./cli/evidence/memory-store-2026-10-29/cli-kernel-regression.tap) 和 [Vitest JSON](./cli/evidence/memory-store-2026-10-29/supplemental-regression.json)。本地结果不能替代准确提交上的 GitHub Actions 三系统门禁。

热查询 p95 在三档分别降低约 **49.8% / 43.6% / 4.9%**；100K 的 p50 从 1806.856ms 降至 1388.957ms，但不能用中位数替代 p95 宣称达标。当前热 p95 <200ms 的目标三档均未达到，100K 冷 p95 <1s 也未达到；仍需继续优化大数据档的磁盘与解码成本。单机顺序测量含 OS 缓存与系统负载波动，不据此推导其他平台或固定生产收益。

## 混合进程竞争

8 个独立 Node 进程到齐后由 IPC 屏障同时启动，4 个读取首屏，2 个更新，2 个删除并 purge；每轮确认八项操作的实际时间区间确有重叠。写入使用互不相同的合成记录，仍经生产 CAS 与严格文件锁。按已提交的 revision 重建每一代参考首屏，检查每个 reader 返回的记录摘要；每档结束后全量导出核对全部记录与审计顺序，再遍历默认索引列表确认所有已删除记录均不可见。

| 记录数 | 轮次 / 进程任务 | 并发读取 p95 | 锁等待 p95 | 进程任务吞吐 | 最终 active 数 / revision |
| ------ | --------------- | ------------ | ---------- | ------------ | ------------------------- |
| 1K     | 11 / 88         | 2786.831ms   | 2453ms     | 2.831/s      | 978 / 1066                |
| 10K    | 11 / 88         | 3347.543ms   | 2868ms     | 2.375/s      | 9978 / 10066              |
| 100K   | 11 / 88         | 6430.593ms   | 4756ms     | 1.305/s      | 99978 / 100066            |

三档合计 **132 次读取、66 次更新、66 个删除 / purge 任务**；后两类产生 **198 次提交**。每档删除 22 条，revision 增加 66，最终无遗留锁。吞吐的分母从屏障释放计到子进程退出，不包含 fixture 构造、进程启动等待及最终全量审计；删除任务内部包含两次提交，因此它不是单次磁盘 I/O 或单次提交的吞吐。

证据：[混合竞争原始报告](./cli/evidence/memory-store-2026-10-29/mixed-concurrency.json)。这些结果证明限定负载下的正确性，锁等待和并发延迟仍明显；它没有覆盖崩溃注入、同一记录 CAS 冲突的吞吐、长时间压力或跨平台生产准入。

## 复现

从仓库根目录运行，输出文件应选用尚不存在的新路径：

```bash
node packages/cli/scripts/memory-query-index-benchmark.mjs --counts 1000,10000,100000 --samples 11 --cache-mode validate-disk --output <disk-result.json>
node packages/cli/scripts/memory-query-responsiveness-benchmark.mjs --counts 1000,10000,100000 --samples 11 --require-cancellation --output <stop-result.json>
node packages/cli/scripts/memory-mixed-concurrency-benchmark.mjs --counts 1000,10000,100000 --rounds 11 --output <mixed-result.json>
```

三个测量顺序执行，不同时运行其他本批重负载测试。冷查询指新的 Node 进程，不清空 OS 文件缓存；重建仅移除可派生查询索引，保留权威记录和审计。原始失败基线保留，不按修复后的结果回写。
