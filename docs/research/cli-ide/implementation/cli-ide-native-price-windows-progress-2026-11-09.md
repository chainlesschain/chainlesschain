# 原币分时结算与过期后恢复（2026-11-09）

对应差距复核第 3、5 项。本批实现显式可信宿主中的原币分时结算，并修复合约或 FX 过期后无法重新打开账本、结算既有派发请求的问题。真实账号价格、账单和正式付费准入仍待验收。

## 合约与派发绑定

`FormalBudgetAuthority` 沿用已有的账号合约、FX、历史核对、独立 lineage registry 和 checkpoint host 验证。可选合约字段为：

- `pricingTimeBasis: "host-dispatch"`：可信账号凭证必须明确证明价格按宿主派发时刻确定。公开价目表、provider 响应的 `created` 或用户输入不能证明这项计费规则。
- `pricingWindows`：最多 4096 个按顺序排列的绝对 UTC 毫秒区间，采用 `[validFrom, validUntil)`。区间必须无缺口、无重叠，完整覆盖合约有效期；每个区间具有唯一 `id`。
- 每个区间恰含 `id`、`validFrom`、`validUntil`、`inputMicrosPerMillion`、`cachedMicrosPerMillion`、`outputMicrosPerMillion`、`fixedFeeMicros`。金额是合约原币的整数微单位；所有费率和固定费用均不得超过原有顶层预留上界，缓存价不得高于输入价。

合约 verifier 的 subject digest 覆盖完整时段表。修改时段或价格会使原凭证失效。时区、重复每日时段和节假日规则须由可信宿主根据账号合同转换成完整绝对区间；当前实现不从本机时区或公开网页推测这些规则。按 provider 接收或完成时刻计费的账号不能用 `host-dispatch` 冒充已验证。

预留仍使用最坏情况下的顶层价格。异步凭据准备之后，authority 在一次 SQLite 事务内把派发状态和 `{dispatchedAt, windowId}` 同时持久化；只有事务完成后，现有 transport 才执行物理请求。结算通过这份唯一持久化见证选择价格，不采用响应时间或恢复时的时钟重新选择。输入、缓存、输出、固定费仍按既有整数算法计算原币金额，再按已验证的有理数 FX 上界向上取整为 USD。

见证缺失、重复、格式异常或与合约不一致时，结算保留完整预留并停止后续派发。派发见证保存失败时，不发送 provider 请求。未定 usage、取消和中断仍沿用既有未知负债规则；有效时段表不能释放未知费用。

## 恢复修复

新增回归先复现了实际缺陷：持久化账本在合约与 FX 到期后，构造函数按重启时刻重新执行激活校验，因过期而拒绝打开；已派发请求因此也无法结算。

现在重新打开时，校验唯一的原始激活记录、activation digest 和可信时间，再按原始激活时刻核验已固定合约。新的预留、凭据读取和实际派发仍通过 `#contract` 检查当前合约与 FX 有效期。已持有但未派发的过期请求仍被拒绝；已派发请求可以按原价格与 FX 结算。没有新增 allowance、自动迁移、重新初始化或未知请求重放。

## 验证范围

使用合成账号凭证、CNY 价格和 FX 夹具，不调用付费 provider。验证包括时段边界、等待凭据时跨时段、关闭重开、真实独立 Node 进程 SIGKILL 后恢复、过期后结算、重复结算、账本写入失败、损坏见证和原始激活记录，以及既有多进程预算/取消/反回滚边界。

正式准入开关仍为 `paidReady:false`。`cc cost` 的固定 USD 估算器没有继承或猜测 CNY 价格。Volcengine 的实际账号时段规则、合同、FX 费用上界、发票核对和三系统结果仍需各自证据，不能由这些离线夹具替代。

此外，锁文件隔离构建恢复了预算审计所需的 Web Panel 生成资产。现有 Volcengine 实施诊断脚本的已提交差异已逐项审查，并更新其过期的源码摘要与说明；分类仍为 `MODEL_REQUEST`，没有提高付费 readiness。
