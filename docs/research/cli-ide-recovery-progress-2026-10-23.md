## 已复现并修复

| 问题                                                                         | 修复后的行为                                                                                                   |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| SDK 直接返回 `Writable.write()` 的背压值，把已经排入管道的输入报告为发送失败 | 已排队输入返回 `true`；持久接受仍须核对 CLI 回执，背压不触发补发                                               |
| SDK 未监听 stdin 的异步 `EPIPE`，错误可能逃逸到宿主                          | 向 SDK `error` 监听者报告错误，禁止后续写入，并继续排空 stdout 中的最后回执或结果                              |
| VS Code 在管道失败、关闭输入或信号退出后仍可能报告发送成功                   | 已失败或结束的输入通道拒绝新写入；进程 `exit` 立即结束发送资格，`close` 仍负责排空输出                         |
| VS Code 持久提交包装器忽略底层失败，仍返回成功                               | 如实返回失败；已进入写入边界的保存记录继续保持 `unknown`，不标记为拒绝或自动重发                               |
| JetBrains 一次部分写入失败后仍为后续输入预留交付身份                         | 锁住失败的输入通道；原输入保留未知结果，后续提交在预留前拒绝；界面引导查询 Saved inputs                        |
| Windows 连续保存草稿偶发 `EPERM rename`，整轮保存提前失败                    | 对 Windows 的 `EPERM`、`EACCES`、`EBUSY` 最多执行六次原子替换，退避总计最多 620 ms；每次重试前重新核对页面身份 |

草稿重试始终保留旧清单，沿用同一个已同步并关闭的临时文件；没有先删除目标或放宽访问权限。永久拒绝仍返回原错误并清理临时文件，原草稿与附件可恢复。页面已切换时不继续发布过期内容。

SDK 从 TypeScript 源码重新构建，并通过现有同步脚本更新 VS Code 和桌面端的 vendor 副本。两个副本的字节一致，源码与生成输出摘要检查通过。

Astra 已将首轮安全失败定位到 DOMPurify critical 漏洞。根覆盖规则、桌面与 Web Panel 清单及所有对应锁节点升级至 **3.4.17**，包括 Monaco 的嵌套副本；原审计门 `audit-check.js --audit-level=critical` 本地通过，DOMPurify 审计项消失。既有 decompress 豁免保持原状，不能把此结果表述为所有依赖 critical 数量为零。新 DOMPurify 官方明确不支持 happy-dom；Web Panel 的两个原清洗测试改用受支持的 jsdom，保留所有断言，**11/11** 通过。桌面原清洗测试在隔离无关全局 setup 后 **11/11** 通过；默认配置因本地缺 pinia 未执行，仍由完整 CI 验证。

Windows 旧版 VS Code 失败已定位到 Electron 主进程退出阶段：此前 DOM 与 100 次采样通过，扩展宿主正常退出，然后 `app.quit()` 发生原生访问违例。缺少原始 dump，尚不能确定原生故障模块。本轮仅增加 `main.log` 和不上传到厂商的本地 crash dump，CI 单独保留 dump 三天；没有忽略非零退出或降低宿主要求。Astra 本地旧宿主没有重现崩溃，但因性能 P95 超限正确失败，不能计作发布通过。

新 CLI 配对的发布约束与 changelog 检查 **26/26**、IDE 元数据检查 **25/25**，以及 JetBrains 新推荐版本的 Gradle 编译与 **14/14** 测试通过。一次额外本地模型定价契约检查因缺少 better-sqlite3 原生绑定失败，原报告保留，未改断言或计作通过。所有候选仍须由自己的准确提交取得完整 Actions 门禁。

提交 `059bad9c26` 的 Windows CLI Reliability Soak 又发现一个失败：MCP 子进程在模型请求前退出（exit 1、stdout 0、stderr 180 字节），随后慢速管道场景只报“无输出”。原始 [失败收据](./cli/evidence/recovery-2026-10-23/release118-windows-soak-before.json) 保留。现存采证丢弃了启动错误，并可能在注册退出监听前漏掉提前退出，失败时还会丢失此前样本；提交 `304733022a` 补充受限启动分类、即时进程生命周期观察和失败场景快照，不修改期限或通过条件。其新 CI 继续保留 Windows 零输出失败，并显示 macOS 和 Linux 的不同故障。本地诊断中的 `ERR_MODULE_NOT_FOUND` 字面量来自 `CLAUDE.md` 提示词内容，不能用它判断缺少模块；此前的缺模块推断撤回，本地失败仍未计作通过。

Astra 将 macOS 的第一模型请求前失败隔离到 `.claude/rules/encoding.md` 的合法 JavaScript 示例：数组中的字符串拼接被当成损坏 JSON。现在仅对直接消息文本中闭合、明确标注受支持 JavaScript / TypeScript / Python 语言的代码块复用已有代码字面量扫描；未知语言、JSON 或未闭合代码块保持严格校验。敏感字段扫描、重复键拒绝和跨代码块累计预算不变。Agent 投影规则升级至 v5，原 v4 摘要及历史回放逻辑保留。真实项目规则回归与投影相关测试 **195/195** 通过。

Windows 另有版本兼容问题：Node 22.12 的 libuv 1.49.1 将 64 位卷序列号暴露为 `stat.dev`，两个 Win32 目录 API 返回 DWORD。直接比较会误拒合法 NTFS 目录。修复仅在这两处跨接口比较时取低 32 位；路径前后完整 `dev`、文件 ID、固定盘、NTFS、重解析点和 flush 前后身份检查均保留。真实原生 API 配合旧版 64 位表示的对照在修复前拒绝、修复后通过，专项 **6/6** 通过；它使用本地 Node 22.22.2，不冒充 Node 22.12 真实本地运行或远端通过。Astra 独立复核未发现阻断问题。上述两个修复仍须新提交的完整准确 SHA Actions 验证；所有候选继续未发布。
